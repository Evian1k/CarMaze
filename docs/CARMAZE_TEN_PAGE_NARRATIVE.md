# CARMAZE — THE TEN-PAGE STORY

*A single continuous narrative covering everything the founder specified, written after a full re-inspection of the codebase on 8 November (five parallel inspection sweeps covering the repository structure, the 99-model database schema, all 154 API route files, all 22 library modules, and all 28 views plus 115 component files). Every statement below reflects what the code actually contains today; implementation status is stated plainly wherever something is partial, unconfigured or absent. This narrative is a companion to the 20-file documentation suite indexed in `CARMAZE_COMPLETE_PLATFORM_DOCUMENTATION.md` — read it when you want the whole platform in one sitting rather than in sections.*

---

CARMAZE is a Kenya-first automotive ecosystem built as a single web application whose ambition is to connect every participant in the life of a vehicle — buyers, private sellers, showrooms, garages, parts suppliers, delivery partners, inspection/insurance/towing partners, and the platform's own operations staff — into one coherent product with one identity system, one database, and one set of trust rules, because the founder's diagnosis of the Kenyan market is that the problems there are not caused by a shortage of cars or a shortage of buyers but by the absence of trustworthy plumbing between them: classifieds are full of unverified sellers and fake documents, showrooms and garages run their businesses on WhatsApp and paper, customers hand their vehicles to strangers with no recorded handover, and garages buy parts with no fitment certainty and no payment protection. The platform therefore refuses to be "just a listings site" and instead ships twelve interlocking surfaces in one Next.js 16 application on one SQLite database — the public Marketplace for searching and comparing vehicles, DealerOS for showrooms, GarageOS for garages, the Supply Network plus SupplierOS plus the Procurement portal for the parts trade, LogisticsOS for the delivery fleet, My Garage and the Vehicle Protection custody system for owners, the 3D Customizer, the Community, Memberships with a business-controlled credit ledger, Roadside assistance, the Partner Network, and the staff-only Control Center — all sharing one authentication system, one `Org` business model, one notification pipeline, and one demo sandbox. What makes this codebase unusual is not the feature list but the honesty policy baked into it: the code deliberately never simulates a successful payment, never lets an upload self-verify a business, never lets a demo account touch a real customer's data, and records failures rather than hiding them, and this narrative will keep that same standard throughout.

Architecturally the whole product lives inside a single client-side single-page application hosted by the App Router: `src/app/page.tsx` is the only page, it is a `'use client'` component that owns a custom hash router (so real URLs look like `#/cars`, `#/dealer`, `#/garage-dashboard`, `#/supply`, `#/procurement`, `#/logistics`, `#/memberships`, `#/my-garage`, `#/admin?tab=demo`, `#/account`, `#/signin` and so on), it lazily imports 28 view modules from `src/views/` with `ssr: false`, guards each view with a role map in `src/lib/view-guard.ts` that is explicitly documented as a UX convenience rather than a security boundary, and wraps everything in an `AppShell` that renders the header, navigation, notification bell, command palette, mobile tab bar, footer, and the amber demo banner. The true security boundary is the backend: 154 API route files under `src/app/api/` exporting 244 HTTP handlers, almost all of them funneled through a `route()` wrapper in `src/lib/api.ts` that normalises errors (Zod validation failures become 400 `VALIDATION_ERROR`, business rule violations become `ApiError`s with explicit codes like `FORBIDDEN`, `INVALID_TRANSITION`, `MPESA_NOT_CONFIGURED`, `DEMO_SANDBOXED`, and everything else becomes a 500), enforces authentication with `requireUser()` and role checks with `requireRole(...)`, and logs 206 audit call-sites across 94 files into an `AuditLog` table. There is no `middleware.ts` at all — every endpoint re-reads the acting user from the database on every request via `getSessionUser()`, which is itself the enforcement mechanism for suspensions, because a suspended user's session cookie still verifies cryptographically but the database lookup returns nothing. The data layer is Prisma 6 over SQLite (`db/custom.db`, about 1.6 MB) with 99 models and zero native enums — SQLite cannot store enums, so every status vocabulary from vehicle listing states to purchase-order lifecycles is a `String` column with allowed values documented in schema comments and mirrored in label maps in `src/lib/format.ts` — and all money everywhere is stored as integer minor units (cents) with an explicit currency default of `"KES"`, so a KES 4,900 plan is the integer 490000 and the frontend formats it back with an `Intl.NumberFormat('en-KE')` helper.

Identity and access control is the spine of the system and operates in three deliberate layers. The first layer is the platform role system: the `User.roles` column holds a comma-separated list from sixteen constants defined in `src/lib/auth.ts` — `CUSTOMER`, `SELLER`, `SELLER_VERIFIED`, `DEALER_OWNER`, `DEALER_STAFF`, `GARAGE_OWNER`, `GARAGE_STAFF`, `SUPPLIER_OWNER`, `SUPPLIER_STAFF`, `LOGISTICS_OWNER`, `SUPPORT`, `REVIEWER`, `MODERATOR`, `FINANCE`, `ADMIN`, and `FOUNDER` — where every registration grants `CUSTOMER,SELLER` automatically, business roles are granted only when staff approve an application, and the six staff roles form the `STAFF_ROLES` list that gates the Control Center. The second layer is business membership: one unified `Org` table (type `DEALER`, `GARAGE`, or `SUPPLIER`) with an `OrgMember` join table whose role column encodes dealership roles (`OWNER/MANAGER/SALES/FINANCE/STAFF`), garage roles (`OWNER/MANAGER/MECHANIC/STAFF`), and, in the supply domain, a genuinely granular permission matrix in `src/lib/supply.ts` that maps twelve named actions (`catalogue.write`, `stock.write`, `order.create`, `order.approve`, `payment.initiate`, `dispute.open`, `finance.read` and so on) against six supplier business roles and seven garage business roles, so a garage mechanic can create nothing above a stock alert while only an OWNER or GM can approve a purchase order above the org's configured `poApprovalThresholdMinor`. The third layer is tenant isolation: rather than a naive `organizationId` column on everything, queries derive the tenant server-side from membership — `requireOrgMember()` in `src/lib/supply.ts` is the documented "single tenancy gate" for the entire supply domain, vehicle `?mine=1` listings are restricted to rows owned by the user or by an org they belong to, invoice listings are scoped to `OWNER/MANAGER/FINANCE` memberships, and spoofing an `orgId` you do not belong to returns 403 `NOT_A_DEALER_MEMBER`. Sessions themselves are stateless JWTs in an httpOnly, sameSite=lax cookie named `carmaze_session`, signed HS256 with `AUTH_SECRET` (which has a hardcoded development fallback because the deployment `.env` contains only `DATABASE_URL` — a known production checklist item, not a hidden secret), defaulting to seven days for real users, while passwords are bcrypt-hashed at cost 10 and optional TOTP multi-factor authentication is implemented from scratch in `src/lib/totp.ts` as a genuine RFC 6238 implementation with base32 secrets, a five-minute scoped challenge JWT, and constant-time comparison. The demo system rides on top: eight role keys (`customer`, `private-seller`, `showroom-owner`, `showroom-staff`, `garage-owner`, `garage-staff`, `platform-support`, `platform-admin`) map server-side to seeded accounts whose emails never reach the client, sessions carry a `demo` claim that is decoded for display but never trusted for authorization, session length is clamped by `DEMO_SESSION_MINUTES_MAX = 14 * 24 * 60` (the two-week timer you asked for and verified end-to-end: the API validates PATCH requests against that ceiling, the database stores `sessionMinutes: 20160`, and the banner counts down in day-and-hour form), and four server guards — `assertDemoResourceGuard`, `demoStaffMutationGuard`, `assertNotDemoActor`, and `assertNotDemoStaffRead` — make the sandbox real rather than cosmetic: demo users cannot initiate payments, cannot read KYC documents or the audit trail or revenue, cannot mutate platform-wide settings, and notifications from a demo actor to a non-demo user are silently dropped.

The customer journey begins on a homepage that reads its hero content from the editable `SystemSetting` store and its live inventory from `GET /api/vehicles/home`, then moves into the Marketplace at `#/cars`, which is the most-polished surface in the codebase: filters draft into a shareable URL with a 400-millisecond debounce, results paginate against real `PUBLISHED` vehicles with compound indexes on status-plus-make, body type, price, county and creation date, cards carry Featured/Sold/Reserved badges and an amber demo badge where appropriate, up to three vehicles can be compared client-side across a fixed spec table, hearts save vehicles optimistically with rollback, searches can be saved with alerts, and an AI car-finder section accepts a natural-language brief and returns matches constrained to real published inventory. A vehicle detail page shows the gallery, full specification, honest safety guidance, the seller or storefront card, similar listings, a fire-and-forget view counter with IP-hash deduplication, and dialogs to enquire (with phone-share consent), report a listing, message the showroom, or book a test drive; everything the buyer does afterwards — enquiries, offers, quotes, bookings, orders, subscriptions, rewards, protection records, test drives, notification preferences — lands in the twelve-tab Account dashboard, while their owned vehicles live in My Garage as personal records with service history entries and maintenance reminders that are intentionally owned by the user, not by any garage, and cross-referenced into the custody system when a car actually goes into a workshop.

The private seller path is deliberately simple but not naive: a seller creates a listing through the three-step wizard at `#/sell` (basics, pricing, reach) with photos intended to upload through `POST /api/upload` — and here must be recorded the single biggest functional gap discovered in the entire inspection: **the `/api/upload` route does not exist server-side**, even though eleven client call sites across selling, applications, custody documentation, delivery proof-of-delivery, and messaging send files to it, while both of its serving siblings (`GET /api/files/[name]` for protected documents and `GET /api/media/[name]` for public marketplace media) do exist; uploads therefore fail today, and this is flagged in the limitation ledger as the highest-priority build item. Listings are created as `DRAFT` or `PENDING_REVIEW` and cannot reach `PUBLISHED` by themselves — only staff moderation action in the Control Center flips a listing, writing a `ListingEvent` timeline row, notifying the owner, and auditing the change — and a seller who wants the verified badge must submit a real KYC application with documents that land in the per-document verification state machine (`SUBMITTED → UNDER_REVIEW → MORE_INFO_REQUIRED/VERIFIED/REJECTED/EXPIRED/SUPERSEDED`) where every staff view of a document is itself written to a `DocumentAccessLog`. Once live, the seller manages everything from `#/my-listings`: status transitions, offer accept/reject with expiry, enquiry threads, and deletion.

DealerOS is the showroom's entire operating business rather than a dashboard chrome: an unverified visitor to `#/dealer` sees marketing and a four-step application wizard that creates an `Application` (type `DEALER`) with uploaded documents, SLA metadata (`reviewSlaHours` default 24), escalation and reminder counters, and a full `ApplicationEvent` timeline; while the application is in review they see an honest status card with a resubmit path; once approved they get a twelve-tab portal — overview with the rule-based Dealer Copilot (which the code explicitly labels "deterministic, insight computed from REAL data. No AI"), inventory with plan-enforced `listingLimit` and `featuredLimit`, branches with inter-branch vehicle transfers, enquiries, an inbox with unread state per side, offers, test-drive management with odometer and fuel check-in/check-out fields, a buying-requests board, membership programme management, staff seats enforced against the plan's `staffLimit` with OWNER-only invites, billing that creates PENDING invoices, and profile/storefront editing — and the Owner-versus-staff distinction is enforced identically on both sides: the frontend hides what a staff member cannot touch, and the backend independently rejects it, because every staff-capable endpoint re-checks membership role rather than trusting the UI.

GarageOS carries the platform's most safety-critical innovation, the vehicle custody lifecycle, which exists because handing a car to a workshop in Kenya is an act of trust with no record; CARMAZE makes the handover a recorded digital event beginning when the customer (or a garage via the storefront handover dialog) creates a `VehicleCustody` record with an `HC-` reference code, condition photos, declared valuables, an odometer and fuel reading, an authorised spend cap, and an explicit road-test consent flag, then walks an eleven-state machine — `HANDOVER_REQUESTED → RECEIVED → INSPECTION → AWAITING_APPROVAL → WORK_IN_PROGRESS` with an optional `ROAD_TEST_REQUESTED` branch that the customer must authorise or decline before a technician may drive the car (with start/end odometer capture and an incident flag that triggers extra notifications) — through `READY_FOR_COLLECTION`, where the garage records completed work and final odometer, and ends at `RETURNED` either in person or through the named-collector flow in which the customer generates a single-use six-digit collection code that is bcrypt-hashed with a 48-hour expiry (re-issue invalidates the old code, failed attempts are audited as `COLLECTION_CODE_FAILED`, and only the custody's owner can authorise it). Every transition writes a `CustodyEvent` with actor side and note, and a dispute at any point flips the record to `DISPUTED`, auto-creates a `SecurityIncident` of category `DAMAGE_IN_CUSTODY`, and notifies platform staff — a workflow that is fully implemented on both sides of the API and wired through the GarageOS custody tab and the customer's Vehicle Protection panel. Around that core, GarageOS also manages the service catalogue with `priceFromMinor` anchors, quote responses against customer service requests (one quote per org per request, enforced by a unique constraint), a bookings lifecycle of `CONFIRMED → IN_PROGRESS → COMPLETED` that mirrors onto the parent request, reviews, branches, memberships, and the procurement portal launcher.

The Supply Network is the deepest and most industrial system in the codebase, spanning the public `#/supply` catalogue with fitment search that returns honest `MATCH/POSSIBLE/NO_FITMENT` verdicts rather than guesses, verified supplier storefronts with per-warehouse stock visibility, a garage Procurement portal with a multi-supplier cart persisted to localStorage through crash-proof storage wrappers, RFQs (`QuoteRequest` with competing `QuoteOffer`s from suppliers), and a nine-step purchase-order lifecycle — `SUBMITTED → AWAITING_APPROVAL → ACCEPTED/REVISED → CONFIRMED → DISPATCHED → IN_TRANSIT → DELIVERED → INSPECTED → COMPLETED`, with `CANCELLED` and `DISPUTED` branches — in which approval above threshold requires OWNER/GM, dispatch is blocked unless payment status is `PROTECTED` (a supplier cannot mark their way past the gate), handover requires a six-digit OTP or QR token verified against a bcrypt hash with one-confirmation-then-two-confirmation finalisation and photo evidence, inspection records per-item accepted quantities that drive stock fulfilment and automatic partial refunds for shortfalls, and release computes the platform commission from editable `SystemSetting` fees (defaults: 3% supply commission, 5% delivery commission, a KES 50 minimum, plus vehicle-sale 1.5%, booking 2% and membership 5% rates) before recording `RELEASED` or `PARTIALLY_RELEASED`. The money-protection model must be described with precision: `PaymentAuthorization` is an escrow-style status machine — `PENDING → PROCESSING → PROTECTED → RELEASED/PARTIALLY_RELEASED/REFUNDED/FAILED` — where `PROTECTED` can only be set by a verified provider callback, never by supplier action, and disputes freeze `amountFrozenMinor`; but the codebase itself documents that no real funds are moved anywhere, because release writes the split into the database and the audit log without any payout API, making protection a rigorous ledger rather than a custody account. Alongside B2B procurement there is a deliberately separate consumer path: `CustomerOrder` with its own state machine, delivery OTP, invoice linkage and disputes, so a member of the public buying brake pads never touches the garage-supplier machinery. The SupplierOS portal manages the catalogue end (products with SKU uniqueness per supplier, category tree, wholesale tiers with minimum quantities, tax and warranty fields, compatibility matrices sourced from supplier or admin, provenance metadata where `authenticityVerified` can only be set by platform admins, per-branch `ProductStock` with reorder levels and a full `StockMovement` ledger, price history, and stock alerts garages can subscribe to) plus orders, consumer orders, RFQ responses, warehouses and billing.

The remaining surfaces knit the ecosystem together: LogisticsOS runs a partner network with its own application pipeline, driver and fleet management, an open job board, and OTP/QR-verified proof-of-delivery with photos across a `OPEN → ASSIGNED → PICKED_UP → IN_TRANSIT → DELIVERED/FAILED/CANCELLED` lifecycle; the Partner Network is a human-verified directory across seven categories (inspection, insurance, finance, towing, parts, transport, other) with tracked referral requests and an apply flow; Memberships let businesses define customer tiers with monthly/yearly pricing, benefit catalogues, per-period redemption keys that prevent double-redemption, and a `BusinessMembership` lifecycle gated on payment like everything else; a private Trust Programme labels customers `NEW → REGULAR → LOYAL → PREFERRED → TRUSTED` with suspensions; a business-controlled `CreditFacility` ledger records signed entries with running balances against deposits and limits; and a platform-level `LoyaltyLedger` awards points for referrals (500 at signup, capped), reviews and completed services. The Community is a moderated feed with categories, polls, reactions, comments and reporting; Roadside assistance coordinates towing and battery/tyre/fuel/lockout help with explicit "not an emergency service" disclaimers; and the 3D Customizer is a genuine three.js/WebGL configurator whose configurations persist with a share ID and can be dispatched to garages as modification quote requests.

The AI layer is small, honest and fully instrumented: exactly three routes import the z-ai SDK, and all three are chat completions with thinking disabled. The Car Finder converts a buyer's prose into a JSON filter object that is then passed through a strict `coerceFilters` function which drops untrusted fields, clamps enums and ranges, and queries only real published vehicles — the prompt literally instructs the model never to invent vehicle data, so the AI narrows the search but the database supplies the truth. The Garage Assistant converts symptoms into general guidance plus one to three service categories drawn from a whitelisted twelve-value list, explicitly refusing to diagnose. The Listing Assistant turns seller-supplied facts into an 80-to-150-word description under an instruction not to invent specifications. Every attempt — success or failure — writes an `AiUsage` row with feature name and truncated error, failures return 503 `AI_UNAVAILABLE`, and rate limits run 15/hour authenticated (5 anonymous) for car-finder and 10/hour for the other two. The Dealer Copilot, by contrast, is rule-based by design and says so in its own source comments. There is no image generation in any API route, no conversation history, no valuation model, and no AI output is stored as content — the seller saves their own description, and search results are recomputed from the database.

Payments deserve their own paragraph because the platform's integrity depends on getting their status exactly right: the only provider integrated is Safaricom Daraja M-Pesa, implemented for real in `src/lib/mpesa.ts` with OAuth, STK push, and callback parsing; but the deployment `.env` contains only `DATABASE_URL`, so without `MPESA_CONSUMER_KEY`, `MPESA_CONSUMER_SECRET`, `MPESA_SHORTCODE`, `MPESA_PASSKEY` and `MPESA_CALLBACK_URL` every push attempt records a `PaymentAttempt`, marks it honestly `FAILED`, and returns 501 `MPESA_NOT_CONFIGURED` — the code comments state in plain language that a successful payment is never simulated, and `GET /api/health` reports `mpesa: 'not_configured'`. Subscribing to a plan (Dealer Starter KES 4,900, Dealer Pro KES 9,900, Garage Basic KES 2,900, Garage Pro KES 5,900 monthly, plus supplier plans and two campaign packages at KES 1,500/7 days and KES 3,000/3 days) creates only a PENDING invoice; the subscription is activated exclusively by a verified M-Pesa callback (`ResultCode 0`, signature-checked via an optional shared secret with timing-safe comparison that is fail-closed in production, idempotency keys, and amount-mismatch rejection) or by a FINANCE/ADMIN/FOUNDER manual reconciliation that requires a reconciliation note and cascades entitlements while auditing `INVOICE_PAID`. There is no Stripe, PayPal, Flutterwave or Paystack anywhere in the codebase, demo accounts are hard-blocked from initiating any payment, and every revenue figure in the admin console is therefore either a recorded local state transition or a pending invoice — never a fabricated number.

Messaging and notifications are similarly honest about their boundaries. Conversations are org-versus-customer threads with kinds (`GENERAL/QUOTE/BOOKING/VEHICLE_ENQUIRY/SUPPORT`), unread flags per side, archive flags, last-message previews, attachment metadata, and system notes from a null sender, with participant checks enforced server-side and org-side fan-out notifications restricted to `INBOX_NOTIFY_ROLES`. Notifications always write an in-app row, and then — this is the part that must be understood before go-live — email and SMS delivery rows are always written as `FAILED` with an explanatory `lastError`, because a constant `EXTERNAL_CHANNELS_IMPLEMENTED = false` in `src/lib/notify.ts` guards what the code calls an honesty note: even with `SMTP_URL` or `SMS_API_KEY` set, nothing would send, so the system refuses to record `QUEUED` or `SENT` for channels it cannot actually deliver. There is no WebSocket transport anywhere (the `mini-services/` folder is empty and the websocket example is scaffold residue), so unread counts arrive via polling `/api/auth/me`; email verification and phone verification generate six-digit codes that are stored in plaintext on the user row and returned to the client as a labelled development code when no provider is configured, and password reset tokens by contrast are cryptographic, stored only as SHA-256 hashes with a 60-minute TTL and one live token per user.

It is worth walking the fourteen operational chains the founder asked to be traced, because they show how the modules interlock in practice rather than in isolation. Registration and login are a single zod-validated endpoint pair that rate-limits the public surface, hashes the password, optionally attributes a referral code for loyalty points, and issues the JWT cookie; role assignment never happens at registration beyond `CUSTOMER,SELLER` — every business role arrives only through staff-approved applications, which is the trust pipeline's first gate. A customer enquiry on a published vehicle creates an `Enquiry` with phone-share consent and an `EnquiryMessage` thread visible to both the customer and, scoped by membership, the seller side, where the private seller answers from `#/my-listings` and a dealership answers from DealerOS with org-notification fan-out. A seller submitting a vehicle moves it `DRAFT → PENDING_REVIEW`, at which point it is invisible to the public (the API masks unpublished rows as 404 even to direct fetches) until a moderator publishes, rejects, suspends or features it in the Control Center, each action writing its timeline event, notification and audit row. A showroom lead received through a storefront dialog can be converted into a conversation, an offer, or a test drive with licence confirmation and odometer check-out; a garage lead from the garages directory becomes a `ServiceRequest` that collects quotes with a one-quote-per-garage uniqueness rule, and accepting a quote books the job and mirrors the parent request's status. The garage intake chain is the custody flow already described; the parts chain is the purchase-order chain already described; the payment chain is the honest invoice chain already described; the notification chain runs through the in-app ledger with its FAILED delivery records; and the dispute chain can be opened by either side of a purchase order or by a consumer against an order, freezing protected amounts, spawning `DisputeEvent` timelines, and resolving only through platform staff with a resolution code (`REFUND_FULL`, `REFUND_PARTIAL`, `REPLACEMENT`, `REJECTED`) and note. What the chains collectively prove is that no module writes to another module's tables directly — they communicate through events, notifications, invoices and status fields, which is why the same staff console can safely supervise all of them.

That staff console is itself a seventeen-tab Control Center, and its design rewards a close look because it is where the platform's human judgment lives: overview aggregates live operational health; the applications and verification queues enforce the review SLA with reminder and escalation sweeps (a scheduled `applications/sweep` endpoint that flags overdue reviews); listings moderation publishes or polices the marketplace; the users tab manages roles and suspensions; staff management can only ever grant the four non-admin staff roles, never `ADMIN` or `FOUNDER`; the supply console supervises the B2B machinery; revenue is FINANCE-gated with the editable fee schedule beside it; campaigns, partners, tickets and broadcasts round out operations; settings edits the customer-facing content store; audit exposes the full `AuditLog`; and the demo tab manages exactly the eight-role demo experience — enable/disable per role, session length clamped to the fourteen-day ceiling, and the guarded full reseed — with demo admins seeing a deliberately redacted read-only version of their own tab. The whole console is role-gated per tab in the frontend and independently per endpoint in the backend, and staff demo sessions are blocked from KYC reads, revenue, audit, and any platform-wide mutation.

This is also the point to state plainly what the platform does not have, because the founder's instruction was to distinguish evidence from aspiration: there is no NTSA or government database integration anywhere in the code — vehicle histories, logbook checks and ownership verification are handled exclusively through the human document-review pipeline and must never be described to users as government-verified; there is no escrow account holding funds, only the protected-payment status ledger; there is no guaranteed-response SLA machinery beyond the review timers; and there is no legal compliance certification attached to anything — the compliance file in the documentation suite lists real controls and real gaps side by side and claims no certifications. For the audiences this handover serves, the reading order differs: a founder should read this narrative plus the limitations ledger to understand what exists versus what is promised; a CTO should read the security file first because its gap list (secrets, upload route, code-generation entropy, delivery channels) is the pre-production checklist; an engineer should start with the developer guide's pattern descriptions since every one of the 154 endpoints follows the same four-beat structure; an operations lead needs the role matrix and the Control Center walkthrough because verification queues, moderation, reconciliation and disputes are all human workflows with SLA metadata; and an investor should read the payments and revenue file for the plan structure, the fee schedule and the honest distinction between recorded state transitions and collected cash.

The database itself is the system of record for all of this discipline: 99 models, zero enums (every vocabulary is a documented string), 86 cascade relations and two deliberate `SetNull` relations on verification documents so that deleting an org does not destroy KYC evidence, an eleven-event-timeline family (`ListingEvent`, `CustodyEvent`, `POEvent`, `DeliveryEvent`, `ApplicationEvent`, `IncidentEvent`, `DisputeEvent`, `VehicleTransferEvent`, `CustomerOrderEvent`, `DeliveryJobEvent`, `LogisticsPartnerEvent`) that gives every lifecycle an actor-attributed audit trail, a central `AuditLog` indexed by action and target, money in integer minor units with `KES` defaults, tenancy through the single `Org` model with `OrgMember` membership checks, and a `SystemSetting` table that lets super admins edit fees, policies, FAQs and homepage content without a deploy. The seed file is 107 KB of realistic Kenyan pilot data — eight orgs, eighteen products, six warehouses, twelve vehicles, seven plans, demo purchase orders in all three interesting states (a clean COMPLETED+RELEASED one, a DISPUTED+PROTECTED one, and a fresh SUBMITTED one), custody records, incidents, delivery jobs, memberships, a credit facility, thirteen verification documents, and every demo account marked `isDemo: true` with the public demo password `CarmazeDemo2025!` bcrypt-hashed — and the admin demo-reset endpoint re-runs that seed as a child process behind an ADMIN/FOUNDER guard, a `RESET_DEMO_DATA` confirmation literal, a 3-per-hour limit, and a single-flight lock.

Security posture and its gaps are both real and should be stated together. The strengths: deny-by-default authorization with server-side re-verification everywhere, bcrypt password hashing, genuine TOTP MFA, hashed OTP/collection/reset secrets (with the exception noted below), zod validation on essentially every write, 64 rate-limit call-sites across the API with sensible windows (login 10 per 15 minutes per IP-and-email, registration 5/hour, payments 10/hour, AI 5–15/hour), a 206-call-site audit trail, document access logging, webhook signature verification that fails closed in production, and a demo sandbox enforced by four server guards rather than UI hiding. The weaknesses, all visible in source: `AUTH_SECRET` falls back to a hardcoded development string because `.env` is not configured with a production secret; the six-digit generator in `src/lib/ids.ts` uses `Math.random` rather than `randomBytes` for the verification, dispatch and collection codes (which are hashed at rest, but their generation is not cryptographically strong); the email/phone verification dev-codes are returned in HTTP responses; the rate limiter is in-memory and resets on restart; there is no `middleware.ts`, so all protection is per-endpoint (which the code itself documents as the intended boundary, with a `security/access-denied` telemetry endpoint recording frontend probes); `next.config.ts` sets `typescript.ignoreBuildErrors: true`; the ESLint config disables roughly thirty rules wholesale; and the missing `/api/upload` route stands above all of them as the one feature-level break. None of these are hidden — each is visible in the files named — and the honest summary is that the authorization architecture is production-shaped while the operational configuration (secrets, providers, delivery channels) is still development-shaped by design of the sandbox.

Infrastructure and operations follow the same pattern of simple, truthful machinery: the dev command is `bun run dev` (port 3000, logging to `dev.log`), the database is pushed with `bun run db:push` (there is deliberately no `prisma/migrations/` folder — schema changes go straight to SQLite, so `db:migrate`/`db:reset` scripts would misbehave and are not the workflow), seeding is `bun run db:seed`, quality is checked with `bun run lint`, and production would be a `next build` into `output: "standalone"` followed by `bun .next/standalone/server.js` behind the Caddyfile's reverse proxy (port 81 into 3000, plus the sandbox's `XTransformPort` dynamic-routing handler). There is no Docker, no CI, no `.github/`, no test framework — the closest artifacts are the `verification/security-tests.ts` suite of twenty authorisation scenarios and the runtime sandbox scripts in `.zscripts/` — and a handful of installed dependencies are unused (`next-auth`, `@tanstack/react-query`, `react-hook-form`, `next-intl`, `@mdxeditor`, `@dnd-kit`), while a vestigial Tailwind v3 config sits beside the actual v4 CSS-first setup; none of these break anything, but all belong on the hygiene list. Maintenance therefore means: change schema then `db:push` then update the relevant route and view; add an endpoint by following the `route()` + `requireUser/requireRole` + zod + audit pattern that all 154 existing files follow; extend a role by touching the `ROLE` map, the view guard, and the seed; adjust platform economics through the settings endpoint rather than code; and never trust the frontend alone for anything security-relevant.

The state of the platform, honestly classified: fully implemented and wired end-to-end are authentication and MFA, the demo system with its two-week timer, the marketplace with moderation, DealerOS and GarageOS portals, the custody lifecycle, the supply network's catalogue/fitment/PO/dispute machinery, consumer parts orders, logistics jobs, applications and document verification, memberships/credit/trust/loyalty, community, customizer, storefronts, the admin Control Center with its seventeen tabs, and the notification ledger. Implemented in code but unconfigured by environment are M-Pesa (real code, missing credentials), email/SMS (explicitly unimplemented channels, recorded FAILED), and the production secret.
